# Applications research contributor instructions

Read CONTRIBUTING.md, docs/ORGANIZATION_ALIGNMENT.md, docs/RESEARCH_WORKFLOW.md, the current issue and its comments before changing work. The user's requested scope controls the campaign; reading this repository does not invoke every backlog item.

- Preserve live issue assignees, accepted decisions, evidence histories and concurrent work. Inspect and read back GitHub mutations; do not invent issue numbers, Project IDs, owners, review approvals or completed research.
- Follow the [organization contribution policy](https://github.com/Pick-Your-AI/.github/blob/main/CONTRIBUTING.md). Use focused contributor branches and non-author review. Do not bypass approvals or alter organization access to make progress.
- Applications are distinct from model/runtime/hardware components. Link the existing T1/T4 and market evidence. Never edit or replace research's frozen `contracts/v1`.
- Use the separately versioned local application contract. Incomplete findings belong in research notes. Never fabricate facts, prices, dates, quantities, sources or empty substitutes to make a record pass validation.
- Unknown does not mean false, free, Unsupported or safe. Source checked does not mean independently verified. Human review, rights approval, release and website delivery are separate states.
- New product claims require actual primary-source research. Do not promote synthetic fixtures or discovery leads into real application records.
- Publication rights apply to exact fields and intended uses. Public availability, a repository MIT license or a permissive source elsewhere in a mixed record is not a universal reuse grant.
- No paid trials, scraping campaign, deployment, private/customer data collection or external messages are authorized merely by a research issue.
- Native parent relationships track independently reviewable outcomes. Small tasks/subtasks are checklists; never duplicate native child links in a checklist. Do not delete historical issues or close a parent before its scoped acceptance and consumer handoffs are complete.
- Project fields own status, priority and readiness; labels own type/topic. Do not invent estimates or deadlines. Missing prerequisites must have explicit rationale; keep informational links distinct from native blockers.
- Run the README validation commands and state what passed, what was inspected manually and what remains unverified. Automated validation never awards product verification.
